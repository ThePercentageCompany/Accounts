# PWA release and operations

This upgrade extends the existing Flutter/Bloc, cookie authentication, IndexedDB
read cache, durable outbox and Cloud Run/Google Sheets backend. It does not replace
the accounting database or introduce tokens in browser storage.

## Build and deploy

```powershell
flutter analyze
flutter test
flutter build web --release --no-web-resources-cdn --dart-define=SAAS_API_ORIGIN=https://accounts.thepercentagecompany.com
node tool/build_pwa.mjs
```

Run the manifest generator **after every Flutter web build**, and deploy all of
`build/web` atomically. `tpc-sw.js` contains hashes derived from the release files;
do not deploy the development worker from `web/`. The release bundles CanvasKit
and fonts locally so the app shell has no runtime CDN dependency.

Serve over HTTPS. Keep `/v1/**`, `/internal/**`, OAuth callbacks and private uploads
on the API routes; never rewrite them to `index.html`. Set these hosting headers:

| Resource | Header |
| --- | --- |
| `index.html`, `tpc-sw.js`, `pwa.js`, `flutter_bootstrap.js`, `manifest.json` | `Cache-Control: no-cache` |
| `tpc-sw.js` | `Content-Type: application/javascript`, `Service-Worker-Allowed: /` (or the deployed base path) |
| API and authentication | `Cache-Control: no-store` (already set by the backend) |
| Other unversioned static files | Revalidate; do not give unversioned filenames a year-long immutable lifetime |

For a subdirectory deployment, use Flutter's `--base-href=/your-path/`. The manifest,
worker scope and asset URLs are relative to this base. API endpoints keep their
existing absolute `/v1/` paths.

## Push and server reminders

For the existing Cloud Run project, deploy the updated backend, then run
`PUSH_CONTACT=mailto:your-support-address bash enable-push-cloud-shell.sh` from
`backend/cloud-run` in Cloud Shell. This creates/reuses a private VAPID key pair
in Secret Manager, grants runtime secret access, configures the live service and
creates/updates the authenticated minute scheduler. It does not print private
keys. Redeployments preserve configured push environment values. Choose the
operator contact before executing; do not use the example address literally.

### Notification API endpoints

Use `/v1/companies/{companyId}/notifications` for owner sessions, or
`/v1/employee/companies/{companyId}/notifications` for employee sessions. These
routes use the existing HttpOnly session cookies and enforce tenant/task access.
Employee calls include the existing `X-TPC-Company` and `X-TPC-Employee` context.
Responses are private (`Cache-Control: no-store`); query parameters are rejected.

| Method | Path suffix | Request / response |
| --- | --- | --- |
| GET | base path | `{notifications, unread, pushAvailable, publicKey}`; items include task/workspace IDs, assignment/deadline type, title/body and read state |
| POST | `/read` | `{"id":"notification-id-or-all","read":true}`; use `false` to mark unread |
| POST | `/subscription` | `{"subscription":{"endpoint":"https://supported-push-provider/...","keys":{"p256dh":"...","auth":"..."}}}` from the browser Push API |
| DELETE | `/subscription` | `{}` removes this recipient's subscriptions in the workspace; optional `endpoint` limits removal to one device |

Browser mutations require the configured app Origin and `X-TPC-CSRF: 1`.
`POST /internal/notifications` is a worker-only endpoint requiring verified OIDC
authorization: `{}` schedules all ready workspaces; `{"companyId":"..."}` scans
one workspace. It must not be called directly by the browser.

Successful task mutations through both owner and employee sync enqueue assignment
processing. The minute scheduler creates deadline notifications with no browser
open. The notification bell shows recipient history; explicit notification opt-in
enables Web Push and tapping an alert opens the permitted task.

The notification center/history works without push configuration. To enable actual
closed-app Web Push, deploy the updated backend with `npm ci` and configure:

| Variable | Value |
| --- | --- |
| `PUSH_VAPID_PUBLIC_KEY` | Public VAPID key generated by `web-push` |
| `PUSH_VAPID_SECRET_VERSION` | Pinned Secret Manager version with JSON `{"privateKey":"..."}` |
| `PUSH_VAPID_SUBJECT` | Operator contact, e.g. `mailto:support@example.com` |

Generate keys in a secure operator environment (`npx web-push generate-vapid-keys`),
store the private key only in Secret Manager, and grant the API runtime service
account access to that secret. Do not commit keys or place the private key in
Flutter definitions. Configure all three values together; partial configuration
fails startup. The existing deployment script's environment block needs these
additional values when deploying a push-enabled release.

Configure **Cloud Scheduler every minute** to POST `{}` as JSON to
`${SETUP_WORKER_ORIGIN}/internal/notifications`, with an OIDC token whose audience
is `SETUP_WORKER_ORIGIN` and service account is `SETUP_WORKER_EMAIL`. Grant that
account the existing worker invocation permissions. This endpoint authenticates
using the same verifier as setup jobs. The scheduler fans out per-company Cloud
Tasks; each task rechecks active employee access and current task permissions.

Task mutations also enqueue notification processing. The scheduled scan recovers
queue failures and discovers deadline events even when every browser is closed.
Current reminder choices: at deadline, 15 minutes, 30 minutes, 1 hour, 2 hours and
24 hours before, using the existing Dubai task timezone. Assignment and deadline
events have durable IDs; per-device delivery leases prevent concurrent workers
from repeatedly sending the same event. Web Push is at-least-once: after an
uncertain provider response, notification tags replace duplicate visible alerts.
Expired subscriptions are removed. Permission revocation, completed tasks and
changed deadlines suppress inappropriate pending pushes. Logout removes the
account's registered push subscriptions to protect shared devices.

History is bounded to 500 entries per company and the center returns up to 100
currently visible entries per recipient. The current control registry has an
8 MiB safety limit; monitor capacity and provision a dedicated notification store
before exceeding that existing registry's scale. No notification endpoint may
be an arbitrary URL: supported provider hosts are allowlisted to prevent SSRF.

## Offline and accounting boundaries

* Read snapshots are scoped by API origin, account, company and permissions.
* Cached profile metadata permits immediate local startup for at most one hour
  after a confirmed online session. It contains no cookie, refresh token, password,
  invitation/private code, or OAuth secret. Logout and genuine auth rejection remove
  it. Offline recovery never extends that expiry. Reconnection revalidates access.
* Safe local CRUD: customers, products/services, tasks and draft invoices/quotations;
  task comments support local creation. Local changes are labeled pending until
  acknowledged. Task conflicts still use server versions and explicit correction.
* Posting, issuing, receipts, payments, payroll, reversals, assets and capital remain
  server-validated, retry-safe workflows. Local drafts do not feed financial reports.
* IndexedDB transactions commit overlays and queue entries together. Stable IDs
  survive restarts; Web Locks coordinate same-origin tabs. A browser that cannot
  safely coordinate sync retains work rather than issuing duplicate mutations.
* Startup, foreground, connectivity changes, bounded retry and manual sync drive
  foreground synchronization. Background Sync is opportunistic on supporting
  browsers: the worker delivers an independent safe local operation per partition
  per opportunity and stores its acknowledgement for Dart reconciliation. Dependent
  operations, cross-origin API deployments and financial actions wait for foreground
  sync. Closed-app Dart execution is never required for accounting correctness.
* The worker caches only the release's static resource allowlist. API, authentication,
  uploads and external responses never enter Cache Storage.

## Updates and platform behavior

Install/update controls appear on the account and workspace screens. Updates wait
for explicit selection; the UI warns to finish forms and checks both active queues
and persisted device queues. Other tabs do not reload automatically. Browser/OS
storage eviction remains possible; an unsynced device is not a backup.

| Platform | Expected behavior / required real-device validation |
| --- | --- |
| Chrome/Edge on Android and desktop | Browser install prompt when eligible; offline shell; background sync where exposed; Web Push with permission |
| Safari on iPhone/iPad | Add to Home Screen via Safari; push requires a supported Home Screen web app; foreground sync is the reliable fallback |
| Safari/macOS | Browser installation/standalone behavior varies by OS/browser version; supported Web Push and foreground sync |
| Unsupported/private/restricted browser | Explain installation/permission limitations; retain regular web UI; surface local storage failures |

## Verification

Local verification on 2026-10-08: Flutter analysis reported no issues; 264 Flutter
tests passed with one skipped; all 252 backend tests passed. The release build
completed and Chrome verified installability, offline restart, API cache exclusion,
update discovery and blocking updates with persisted changes, with no uncaught
browser errors. Mobile online/offline and desktop screenshots were inspected.

`tool/verify_pwa.mjs` runs the actual release build in installed Chrome via
Playwright. It verifies installability through CDP, service-worker control, static
allowlisting, offline restart, update discovery and blocking an update when durable
work exists; screenshots go to `build/pwa-verification`. Pass the path to a locally
installed Playwright `index.mjs`:

```powershell
node tool/verify_pwa.mjs <path-to-playwright/index.mjs>
```

Backend tests cover tenant/role isolation, assignment and reminder deduplication,
permission revocation and unsafe subscription endpoints. Flutter tests cover the
existing accounting/CRUD flows, local task overlays, durable background acknowledgements,
profile expiry/logout and responsive layouts.

Before calling a deployed release production-verified, test real authenticated
push delivery, scheduler execution, tap-to-task links, installation and denied
permissions on Android, iPhone/iPad and desktop; verify actual HTTPS routing/cache
headers and updates across two open installed windows. Local automated browser
tests cannot certify a physical device or an unconfigured push provider.
